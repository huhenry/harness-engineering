# Harness Scaffold

Write the missing harness files, propose alongside anything that already exists, never overwrite.

## When to use

- `harness-assess` (or the user directly) points at specific gaps and wants the corresponding files created.
- A repository has no AGENTS.md, PROGRESS.md, feature_list.json, or loop templates at all and needs a starting harness.
- The user names specific gap ids or subsystems to scaffold narrowly (`--only`).

## When not to use

- To decide what to fix first — run `harness-assess` first and act on its ROI-sorted gap list, don't guess.
- To hand-write the content yourself instead of using the tool's templates — every file this tool writes comes from a fixed, whitelisted template set for a reason (see Hard rules).
- On a file the repository owner already customized — that is exactly what the propose-instead-of-overwrite behavior exists to protect; don't second-guess it by deleting the `.harness-proposed` sibling and writing the real path yourself.

## Workflow

1. Locate the scripts, same three-way check as every harness-* skill that wraps a script:
   - `${CLAUDE_PLUGIN_ROOT}` was substituted with a real path → `${CLAUDE_PLUGIN_ROOT}/scripts/`. Normal case for an installed Claude Code plugin.
   - Working inside a harness-engineering repo checkout → `scripts/scaffold.mjs`, relative to the repo root.
   - Neither → this skill was installed by copying only `skills/` into another ecosystem (no `scripts/` present). Ask the user for a harness-engineering checkout path, or point them at https://github.com/huhenry/harness-engineering. Do not guess a path.
2. Dry run first, always: `node "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.mjs" <repo>`
   - With no flags, this scaffolds every gap `harness-assess` would currently report as scaffoldable, ROI descending.
   - Narrow it with `--only <gap-id-or-subsystem>` (comma-separated, or the flag repeated) — this is a direct-select escape hatch, not a filter: it names gap ids/subsystems out of the rubric directly and does not itself run assess.
3. Show the full plan table to the user — every row's action (`create` or `propose`) and target path — and wait for explicit approval before writing anything.
4. Apply, only after approval: `node "${CLAUDE_PLUGIN_ROOT}/scripts/scaffold.mjs" <repo> --apply`
5. Report exactly what was written (or the exact point a write failed, and what was written before that) — quote the tool's own output, don't re-describe it from memory.

## Reading the output

- `create` — the target path doesn't exist yet; the file is written there directly.
- `propose` — the target path already exists; the tool writes `<target>.harness-proposed` (or `-2`, `-3`, ... if even that is taken) instead, so the user's existing file is never touched. Review the proposal with the user before they decide whether to adopt it.
- Every generated file carries a provenance marker ("Generated by harness-engineering ... review and fill in before relying on it") except `.claude/settings.json` and `.devcontainer/devcontainer.json`, which are written byte-for-byte unmodified — those are someone else's config schema (Claude Code's own settings format, the Dev Containers spec), not this project's format, and stamping an unrecognized key into either risks a rejected config for no benefit.
- A freshly *created* `init.sh` gets the executable bit; a `.harness-proposed` copy of it never does — don't chmod it yourself, that would nudge the user toward running unreviewed content.
- Dry-run always exits 0. `--apply` exits 1 only if a write actually failed partway through (full disk, read-only mount, permission denied) — that is an ordinary environment condition, not a bug in the tool.

## Hard rules

- Always run dry-run first and show the plan. Never pass --apply until the user has seen and approved the file list.
- Never overwrite an existing file.
- Never write outside the tool's own fixed template whitelist, and never author file content by hand — only the templates the tool itself reads and stamps are ever written.
